# Product Decisions

Decision log for the Culinary Tools Platform. Records approved product/business decisions and rejected alternatives so they don't have to be re-litigated or re-discovered from conversation memory. Maintained by Scribe.

This is a log of **approved** decisions only. Proposals, brainstorming, and Architect design options that were not approved by a Registered Admin do not belong here — see [MISSION_TEMPLATE.md](MISSION_TEMPLATE.md) for how a proposal becomes a decision. Standing system-architecture rules (data authority, storage rules, protected tool integrity rules) live in [ARCHITECTURE_RULES.md](ARCHITECTURE_RULES.md), not here, to avoid duplicating the same rule in two places.

## How to log a new decision

When a mission produces an approved product decision, Scribe adds an entry below with: date, decision, source/approval, and rejected alternatives (if any were explicitly considered and turned down). Do not record a decision that isn't already established in-thread or in existing repo files — if in doubt, ask Chief rather than infer.

## Decisions

### 2026-08-14 - Nessie Global per-plate food-cost pilot
Alex approved a planner-only per-entree plate food-cost pilot for North/Nessie Global in the exact week `Aug 17, 2026 - Aug 21, 2026`. Standard menu plates consist of one selected entree, one automatically identified selected starch/grain base, two selected non-base sides, and every selected sub recipe. Explicit source categories are authoritative for starch/grain bases (including pasta such as Smokehouse `Mac & Cheese`), with a rice/noodle item-name fallback and a salad-category veto. The exact carb-heavy exception menus `AMZ: Piccola Italia`, `AMZ: Lemongrass + Lime`, and `AMZ: Chiang Mai` instead use one entree, one selected side, and every selected sub recipe. Extensions are excluded. When multiple valid bases or sides are selected, the displayed range uses the least- and most-expensive valid plate combinations, and every percentage divides by the entree retail price only. The pilot appears only in the live Nessie Global planner for that week; submitted recaps, Results, summaries, exports, persistence, and every other cafe/week retain existing behavior.
Source: direct request and clarifications from Alex in the current Codex task on 2026-08-14. Admin of Record: Alex Neuse.
Rejected alternatives: adding a separate Base selector; continuing to divide by combined entree-and-side retail; including extensions; applying sub recipes only to selected entrees; immediately scaling the calculation to other stations, cafes, weeks, recaps, Results, summaries, exports, or persistence.
Implementation status note: the initial pilot application commit `0fa3c374cdb5b0629f2ddde456222576ed4788cc` was published and production verified as version `2026.08.14.001-nessie-global-plate-cost-pilot`. Alex's Smokehouse correction shipped in application commit `5f22b9811b2b4fa13da44abcd58a2ad3c389ded3`; Vercel reported production success, the live bundle contains version `2026.08.14.002-smokehouse-starch-base-fix`, and both required browser suites passed 39/39 against production. No schema, persistence, or source-authority change occurred. Release state is `LIVE`.

### 2026-08-01 — Single-final Release closeout and pre-release release-speed safeguards
Tyler approved tightening the deploy-intended release process so the admin-facing thread gets one Release closeout instead of a string of post-deploy chatter, while still preserving independent review, verification, and architecture safety. For deploy-intended releases, Release now owns the single final admin-facing result; Chief does not post a duplicate closing summary afterward, and Reviewer/Verifier/Scribe detailed verdicts stay in working threads unless they surface a blocker. Scribe's detailed record check can stay there too, but one short affirmative Scribe confirmation must still be surfaced in or quoted by Release from the admin-facing closeout before `LIVE` is declared. Tyler also approved four speed safeguards around that closeout: Scribe reconciles `AI_HANDOFF.md` against the release candidate before Release completes production verification; visible/user-facing changes must ship their first implementation commit with a direct automated acceptance test for the exact requested behavior; Builder/Reviewer/Verifier reuse one prepared worktree with dependencies and Playwright browsers already warm; and every Release final report carries a timing block plus avoidable-delay notes.
Source: Culinary Tools Project channel, thread rooted at event `49319ef19d9ae9148dc3f67ca5cbaab360c32f416b15480d9d88736c7422baa2`, Tyler messages on August 1, 2026 asking to reduce post-deploy chatter and then authorizing implementation of all speed recommendations, followed by Chief's scoped process-change assignment on August 2, 2026. Admin of Record: Tyler.
Rejected alternatives: allowing Chief to post a second final deploy summary after Release; discovering stale `AI_HANDOFF.md` only after production verification is already complete; approving visible behavior changes on config/text checks or adjacent suites that never exercise the requested behavior; creating new worktrees mid-mission and treating ownership/browser-install failures as normal release delay; omitting timing and avoidable-delay capture from release closeout.
Implementation status note: process documentation updated in `RELEASE_RUNBOOK.md` and `CHANGELOG.md`; no application code or visible app version change.

### 2026-08-01 — Streamlined deploy-intended default and micro-fix lane
Tyler approved changing governance so ordinary app changes requested by a Release-Authorized Admin are deploy-intended by default. Chief should no longer stop after implementation/review merely to ask for a separate `deploy` message; after the scoped change passes review and verification, Chief continues into Release Gate, production deployment, live verification, and final exact-state reporting unless the request says `do not deploy`, `local only`, or `investigate only`, or a real safety blocker appears. Tyler also approved a micro-fix lane for tiny, well-understood presentation, formatter, stale-test, and documentation/process fixes: one owner, one Reviewer, one Verifier, narrow proof, then Release Gate when deploy-intended.
Source: Culinary Tools Project channel, thread rooted at event `73da3848ad5cc3bc0bcad6c5fdb2b11425a1edd6e9dc458b50019e5249448690`, Tyler messages on 2026-08-01 asking Chief to always understand normal changes as deployment-intended and then to change the governance documents to encourage streamlined deployment. Implementation status note: governance/process documentation updated in `GOVERNANCE.md`, `MISSION_TEMPLATE.md`, `RELEASE_RUNBOOK.md`, `AGENTS.md`, and `CHANGELOG.md`; no application code or visible app version change.
